Field guide

How things break, and how they are caught.

Nine web weaknesses I study in authorized labs. For each one, the question is the same: what goes wrong, what evidence does it leave, and what stops it.

WeaknessWhat goes wrongHow it shows upHow it is prevented
SQL injectionUser input is treated as database code.Odd quotes and keywords in request logs, database errors.Parameterized queries, least-privilege database accounts.
Cross-site scriptingA site runs attacker-supplied script in a visitor’s browser.Script tags and event handlers in parameters, CSP violation reports.Output encoding, Content Security Policy, safe templating.
Broken access control and IDORChanging an ID reveals someone else’s data.One account requesting many sequential IDs.Server-side ownership checks on every request.
Authentication flawsWeak, guessable or unprotected logins.Bursts of failed logins, logins from new places.MFA, rate limiting, lockouts, strong password hashing.
Session managementSession tokens can be stolen or reused.One session used from two places, tokens in URLs.Secure and HttpOnly cookies, rotation after login, short lifetimes.
SSRFThe server is tricked into making requests for the attacker.Server requests to internal addresses or metadata endpoints.Outbound allow-lists, network segmentation.
Security misconfigurationDefaults, debug modes and open services are left on.Probes for exposed admin panels and files.Hardened baselines, automated configuration checks.
File upload flawsUploaded files can run as code or fill storage.New script files in upload folders.Type and size checks, storage outside the web root, no execution.

Detection notes

Every attack leaves evidence.

These are the behaviors Sentinel Detect looks for. One event rarely proves anything, so context and correlation matter.

When an alert fires

A calm, repeatable routine beats a fast guess.

  1. Confirm: is it real, or a false positive?
  2. Scope: what else did this source or account touch?
  3. Contain: cut access without destroying evidence.
  4. Preserve: keep logs and artifacts safe and timestamped.
  5. Fix and learn: patch, tune the detection, write it down.

Stay safe

Security for everyone, not only experts.

Everyday defense

  1. Use a password manager and a unique password for every account.
  2. Turn on MFA, preferring an authenticator app or security key over SMS.
  3. Install updates promptly on phone, laptop and apps.
  4. Back up important files in two places.
  5. Check a link before you tap it.
  6. Install apps only from official stores.

Scam red flags

  1. Urgency or threats such as “act now or lose your account”.
  2. Requests for an OTP, PIN or password. Real banks and wallets never ask.
  3. Prizes or lotteries you never entered.
  4. Job or overseas-employment offers that ask you to pay first.
  5. Investments that promise guaranteed high returns.
  6. A link or number that does not match the real organization.

If in doubt, stop. Do not click or send money. Contact the organization through its official channel, then report the scam.

Password strength check

Type a sample to see an estimate.

The estimate assumes random characters and an offline attack at 10 billion guesses per second. Real passwords follow patterns and fall faster, so uniqueness and MFA matter more than any score.

Learn

The path I’m following.

It’s also the path I’d suggest to anyone starting out. Each step makes the next one easier.

  1. Fundamentals: how computers, networks and the web work.
  2. Linux: the command line, permissions, processes and logs.
  3. Networking: TCP/IP, DNS and HTTP, plus Wireshark to see them.
  4. Python: automate tasks and write small security tools.
  5. Web security: PortSwigger Web Security Academy and the OWASP Top 10.
  6. Guided practice: TryHackMe rooms, then Hack The Box.
  7. Detection: read logs, write rules, map them to MITRE ATT&CK.
  8. Document: write up what you learn and share it.

Ethics

Rules of engagement.

Skill without permission is not research. These rules apply to every lab I run.

  1. Test only what you own or have written permission to test.
  2. Stay inside the agreed scope.
  3. Practice in labs, CTFs and on your own machines.
  4. Protect any data you happen to see.
  5. Report findings responsibly and give the owner time to fix them.
  6. Know the laws where you live.

Glossary

Plain-language terms.

Keep learning with trusted sources:

OWASP Top 10MITRE ATT&CKPortSwigger AcademyTryHackMeHack The Box
Threat

Anything that could cause harm to a system or its data.

Vulnerability

A weakness that a threat could use.

Exploit

A method or code that takes advantage of a vulnerability.

Zero-day

A vulnerability the vendor does not yet know about or has not fixed.

CIA triad

Confidentiality, integrity and availability: the three goals of security.

IOC

Indicator of compromise: evidence such as an IP address, file hash or domain linked to an attack.

SIEM

A system that collects and correlates logs from many sources to raise alerts.

SOC

Security operations center: the team that monitors, triages and responds to alerts.

MFA

Multi-factor authentication: proving identity with more than a password.

Phishing

Tricking people into giving up credentials or running something harmful.

Red and blue team

Red teams simulate attackers. Blue teams detect and defend.

OSINT

Open-source intelligence: analysis of publicly available information.
